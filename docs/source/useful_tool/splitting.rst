Data splitting Tool (``splitting``)
===================================

``splitting`` divides one spatial transcriptomics object into smaller objects that can be reused by downstream workflows. The command is executed directly by Python through ``useful_tool``; it does not start a Snakemake workflow.


- Split by a cell annotation, cluster, or any other field in ``table.obs``
- Split an integrated object by sample, region, or experimental group
- Import ROI selections exported by Loupe Browser or Xenium Explorer
- Crop a rectangular tissue region from a SpatialData object
- Export subset annotations in a format suitable for visualization in Loupe Browser or Xenium Explorer

This page focuses on ``zarr`` objects, although metadata- and ID-based splitting also accepts ``h5ad`` input. For the configuration reference, see :doc:`../config_reference/splitting_yaml`.


Typical use cases
-----------------

1. You have completed ``core_analysis`` and want to isolate one major cell class, such as ``Tumor``, for reclustering.
2. You have an integrated multi-sample object and want to separate it by sample or group.
3. You selected ROIs in external software and want to import the exported CSV files for batch splitting.
4. You want to return a new annotation to Loupe Browser or Xenium Explorer for spatial inspection.
5. You want to focus on a local tissue region, or one slide contains multiple samples that should be separated by coordinates.


Before you start
----------------

1. The input object should preferably be a ``zarr`` path generated by ``integrate``, ``preprocess``, ``clustering``, or ``annotation``. Metadata- and ID-based splitting also accepts ``h5ad`` input, although an ``h5ad`` file does not contain the complete SpatialData images, labels, shapes, points, or coordinate transformations.
2. Identify the observation field used for splitting, for example ``celltype``, ``clusters``, ``sample``, or ``group``. Any valid column in ``table.obs`` can be used.
3. Run the command from the directory containing the relevant data, or use absolute paths.
4. For a SpatialData object with more than one table, set ``table_key`` if the intended table cannot be selected unambiguously. A single table is selected automatically, and a table named ``table`` is preferred when present.
5. Use stable observation or instance identifiers. The tool preserves the original observation names, order, expression layers, ``obsm``, variables, and SpatialData table metadata in each subset.

.. important::

   ``subset_mode=table`` is the default for annotation- and ROI-based splitting. Only rows in the selected table are filtered; the original images, labels, shapes, points, and coordinate transformations remain in the output SpatialData object. This compatibility mode allows the resulting object to be used directly by ``reclustering`` and ``reannotation``. It may not substantially reduce the size of a ``zarr`` store because the spatial elements are retained.

   Set ``subset_mode=spatial`` only when the corresponding Shapes or Points should also be filtered. Raster images are not reduced by a metadata subset; use ``split_by=image`` for a bounding-box crop.


General command template
------------------------

.. code-block:: bash

   spatialsnake useful_tool --option=splitting <INPUT_PATH> --split_by=<mode>

The default settings are read from ``splitting.yaml``. Command-line values override the YAML configuration without changing the Python execution model.


Scenario 1: split by cell type or cluster
-----------------------------------------

Use this mode to isolate one or more annotated populations for downstream analysis. ``split_by`` can be ``celltype``, ``clusters``, or another column present in ``table.obs``.

.. code-block:: bash

   spatialsnake useful_tool --option=splitting results/Colon_Cancer_P2_008um/annotation/Colon_Cancer_P2.zarr --split_by=celltype --barcodes=Tumor

Commas combine labels into one output object:

.. code-block:: bash

   spatialsnake useful_tool --option=splitting results/Colon_Cancer_P2_008um/annotation/Colon_Cancer_P2.zarr --split_by=celltype --barcodes=Tumor,Fibroblasts

This writes one combined object named ``celltype_selected_Tumor_Fibroblasts.zarr``.

Pipes create independent outputs. Because ``|`` is interpreted by the shell, quote the argument:

.. code-block:: bash

   spatialsnake useful_tool --option=splitting results/Colon_Cancer_P2_008um/annotation/Colon_Cancer_P2.zarr --split_by=celltype --barcodes='Tumor|NK_T_Cells'

This writes ``celltype_selected_Tumor.zarr`` and ``celltype_selected_NK_T_Cells.zarr``. The outputs can be listed as separate rows in ``sample.txt`` for parallel ``reclustering``. If ``barcodes`` is empty, one object is exported for every category in the selected field.

Output naming rules:

- Without ``barcodes``: ``cluster_<label>.zarr`` or ``cluster_<label>.h5ad``
- Comma-selected labels: ``<split_by>_selected_<label1_label2>.zarr``
- Pipe-separated groups: one ``<split_by>_selected_<group>.zarr`` file per group

The default table-only mode is recommended for reclustering and reannotation. To synchronize Shapes or Points with the selected table rows, explicitly add:

.. code-block:: bash

   --subset_mode=spatial


Scenario 2: split by sample or group
------------------------------------

Use this mode to organize an integrated object by ``sample``, ``region``, or ``group``.

.. code-block:: bash

   spatialsnake useful_tool --option=splitting results/merge_data/annotation/concatenated_sdata.zarr --split_by=sample

Split by experimental group:

.. code-block:: bash

   spatialsnake useful_tool --option=splitting results/merge_data/annotation/concatenated_sdata.zarr --split_by=group

For ``sample`` or ``region``, SpatialData is filtered by the corresponding coordinate system and written as ``<sample_name>.zarr``. For ``group``, a group that maps unambiguously to one or more complete regions is exported with those coordinate systems as ``group_<group_name>.zarr``. If groups coexist within the same region, the tool filters the table by observation identity rather than incorrectly assigning the complete region to a group.

Output naming rules:

- ``split_by=sample`` or ``region``: ``<sample_name>.zarr``
- ``split_by=group``: ``group_<group_name>.zarr``

Import a CSV file for splitting
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: bash

   spatialsnake useful_tool --option=splitting results/Colon_Cancer_P2_008um/annotation/Colon_Cancer_P2.zarr --split_by=ROI --roi_csv=CRC_P2_simulated_tumor_rich_roi.csv --roi_label_col=ROI

For the CRC Demo, download :download:`CRC_P2_simulated_tumor_rich_roi.csv </config/CRC_P2_simulated_tumor_rich_roi.csv>` into the project root after completing manual annotation.
The command writes ``results/useful_results/data_splitting/ROI_Tumor_rich_region.zarr``.
The Demo selects 17,101 observations and also writes
``ROI_Tumor_rich_region_loupe.csv`` in the same directory. The
100-micrometre distance Demo below is a separate selection.
The CSV is a simulated teaching ROI, not a pathologist-defined region.

``roi_csv`` can be one CSV file or a directory containing multiple CSV files. The format is detected automatically. Supported inputs are:

- A Loupe barcode table, such as ``barcode,ROI`` or another ``barcode,<category>`` table
- A Xenium selected-cell table containing ``Cell ID`` and an optional ROI or grouping column; explanatory lines preceding the table header are accepted
- A Xenium polygon table containing ``Selection,X,Y``; legacy single-polygon ``X,Y`` files are also accepted

Use ``roi_label_col`` when an ID table contains several possible annotation columns and the ROI column is ambiguous. If the file contains only identifiers, its filename is used as the ROI name.

The table's ``spatialdata_attrs`` determine the instance and region keys used for matching. The instance key is preferred, followed by an explicit ``cell_id`` column and then observation names. Matching by row position is never performed. In an integrated object, set ``roi_region`` when identifiers are repeated across regions and the CSV does not identify the source region.

For polygon input, set ``coordinate_system`` if the target coordinate system cannot be inferred uniquely:

.. code-block:: bash

   spatialsnake useful_tool --option=splitting xenium.zarr --split_by=ROI --roi_csv=roi_polygons.csv --coordinate_system=Xenium --subset_mode=spatial

Polygon geometries must contain at least three distinct vertices and be valid. Shape-associated observations are selected when their geometries are fully contained in the ROI; point-associated observations or spot centroids are selected by point-in-polygon. Overlapping ROIs are allowed, so one observation may occur in more than one output.

For every ROI, the log reports the requested, matched, and unmatched identifier counts. Partially unmatched identifiers produce a warning; an ROI with no matches produces an error. Output objects are named ``ROI_<ROI_name>.zarr`` or ``ROI_<ROI_name>.h5ad``.


The splitting result can also be returned to Loupe Browser or Xenium Explorer as an annotation table. By default, ``annotation_format=auto`` exports a CSV when the target format can be inferred. The exported rows exactly follow the observations retained in the subset and preserve their identifier order.

The Loupe-compatible output contains one barcode column followed by one or more annotation columns:

.. code-block:: text

   barcode,celltype,spatial_cluster
   AAACAAGTATCTCCCA-1,Tumor,2

The Xenium Explorer-compatible grouping output contains one annotation per file:

.. code-block:: text

   cell_id,group
   101,Tumor

Use ``annotation_cols`` to export additional observation columns, for example:

.. code-block:: bash

   --annotation_format=both --annotation_cols=celltype,clusters,spatial_cluster

For multi-region input, annotation tables are written separately by region to avoid mixing identifiers that are only unique within one experiment. Set ``annotation_format=none`` to disable annotation CSV output.



.. _splitting-celltype-distance:

Scenario 4: Celltype distance splitting
---------------------------------------

Use distance splitting after annotation to retain a target population together with nearby observations, for example tumor-associated myeloid cells or vessel-adjacent glial cells. ``--distance`` enables this mode; the positional input becomes a sample text file instead of a Zarr path. ROI distance uses the same calculation with targets supplied by an ROI CSV (Scenario 5).

Distance settings and input files
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Distances are calculated in micrometres (µm) from each observation centre to its nearest target centre within the same sample. Multiple target centres form a union of circular neighborhoods; the tool does not use their collective centroid. Neighbors satisfy ``distance_min <= d < distance``. Targets are always retained, including when an inner radius is supplied.

- ``--split_by=celltype --barcodes=Tumor`` selects targets using an existing annotation. Commas combine labels and quoted pipes create separate outputs, as in Scenario 1.
- ``--distance=50`` sets the outer radius in µm. ``--distance_min`` defaults to ``0``; for an outer ring, use ``--distance_min=50 --distance=100``.
- ``--neighbor_col=celltype --neighbor_types=Myeloid_Cells`` restricts non-target neighbors to the specified labels. Without these options, all non-target observations are candidates.
- ``--table_key`` is normally omitted because a SpatialData object with one table is selected automatically, regardless of that table's name. Set it only when the object contains multiple tables.
- ``--subset_mode=spatial`` synchronizes linked Shapes/Points with the selected table; images and transformations remain available. Distance output contains only the selected table and preserves its key, expression data, identifiers, annotations, and original coordinates.

The sample file has five whitespace-separated columns. ``sample_id`` identifies one physical section and matches ``obs['sample']``; ``spatialdata_path`` is the processed parent Zarr; ``raw_dir`` is the matching original platform output directory; ``bin_size`` selects the resolution; ``roi_csv`` supplies ROI targets or is ``-`` for celltype mode. Use ``-`` for unused fields. Save this distinct five-column table as ``samples_distance.txt`` rather than
overwriting the core sample table. All paths inside it resolve from the working directory, and paths containing spaces are not supported.

Platform detection and physical scaling use ``raw_dir`` and ``bin_size`` automatically:

- **Visium:** provide a directory containing ``spatial/tissue_positions.csv`` (or ``spatial/tissue_positions_list.csv``) and ``spatial/scalefactors_json.json``. Full-resolution pixel coordinates are multiplied by ``microns_per_pixel`` when available, otherwise by ``65 / spot_diameter_fullres``. Set ``bin_size`` to ``-``. Spots contain mixed expression; a 50 µm radius often adds no neighbors because centres are approximately 100 µm apart.
- **Visium HD:** provide the directory containing ``binned_outputs`` or the matching ``square_008um`` directory. Set ``bin_size`` to ``2``, ``8``, or ``16`` as appropriate. The selected directory supplies ``spatial/tissue_positions.parquet`` and ``scalefactors_json.json``. Full-resolution pixel coordinates are multiplied once by ``microns_per_pixel``; bin size selects observations and is not an additional scale factor.
- **Visium Segment:** set ``bin_size=cell`` and provide the parent output directory or ``segmented_outputs`` containing ``cell_segmentations.geojson`` and ``spatial/scalefactors_json.json``. Linked polygon centroids are converted from full-resolution pixels using ``microns_per_pixel``.
- **Xenium:** provide the original output directory containing ``experiment.xenium`` and/or ``cells.parquet`` / ``cells.csv.gz``. Table coordinates are already µm; no image scaling is applied. Set ``bin_size=-``.
- **MERFISH (Vizgen MERSCOPE):** provide the directory containing ``cell_metadata.csv`` and ``cell_by_gene.csv`` (or ``.csv.gz``). Imported cell centres are already µm. Set ``bin_size=-``; arbitrary MERFISH formats are not automatically supported.
- **Stereo-seq:** provide the directory containing GEF files, directly or under ``feature_expression/``. Use a numeric ``bin_size`` for the unique ``*.tissue.gef`` or ``cellbin`` / ``adjusted_cellbin`` for the corresponding GEF. Native DNB coordinates are multiplied by ``resolution_nm / 1000`` from the selected GEF; do not multiply again by bin size. For example, bin50 at 500 nm pitch has 25 µm spacing.

Keep the complete parent object as input so that nearby observations outside the target region remain available. One sample means one section; an integrated object may contain biological replicates, but distances are calculated separately for each sample using its own raw directory and scale. ROI distance accepts one sample per run. This is a centre-distance selection, not a tissue-boundary buffer or a test of cell contact.

.. _splitting-roi-distance:

Scenario 5: ROI distance splitting
----------------------------------

Use this mode when a manually selected tissue region defines the targets instead of a celltype label. Supply ``--split_by=ROI`` and an ROI CSV in the sample file; ``--barcodes`` is not needed. The tool first matches ROI identifiers, then retains those targets and the union of their surrounding neighborhoods. Multiple ROI labels produce separate outputs.

Visium, Visium HD, Visium Segment, and Xenium ID CSVs are supported. Xenium Explorer ``Selection,X,Y`` polygons are also accepted in native µm coordinates: linked cell shapes must be fully contained in the polygon before their centres become distance targets. Circle approximations can differ from Explorer's original segmentation at ROI edges; use its exported ``Cell ID`` statistics CSV when exact selected IDs are required. MERFISH and Stereo-seq should use celltype distance mode.

Scenario 6: crop by image coordinates
-------------------------------------

This mode crops the spatial object using a SpatialData bounding-box query.
Bounds must use the selected coordinate system; here they are full-resolution
pixels, not hires image pixels or micrometres.

.. code-block:: bash

   spatialsnake useful_tool --option=splitting \
     results/Colon_Cancer_P2_008um/annotation/Colon_Cancer_P2.zarr \
     --split_by=image --coordinate_system=Colon_Cancer_P2 \
     --min_x=40000 --max_x=55000 --min_y=5000 --max_y=20000

The crop contains 218,032 bins and 16,946 genes. Shapes intersecting
the boundary may have centers just outside the requested rectangle.

The original ``shape_elements`` parameter remains supported. If a SpatialData object contains several coordinate systems, ``coordinate_system`` provides a more explicit alternative and takes precedence when both parameters are supplied. Coordinates may be floating-point values and must satisfy ``min_x < max_x`` and ``min_y < max_y``.

.. figure:: /_static/images/CRC_P2_image_crop.png
   :width: 85%
   :align: center
   :alt: CRC P2 tissue image cropped to the selected coordinate bounds

   Cropped tissue preview; hires is used when available.

Outputs:

- ``spatial<min_x>_<max_x>_<min_y>_<max_y>.zarr``: cropped SpatialData object
- ``<coordinate_id>_shape.png``: spatial preview when an image, Shapes, or Points element is available

Points-only Stereo-seq objects do not require a Shapes element.

Common errors and how to fix them
---------------------------------

1. ``values not found in <field_name>``

   - Cause: values supplied through ``barcodes`` are absent from the selected observation field.
   - Fix: verify spelling, capitalization, and the selected ``split_by`` field.

2. ``multiple tables`` or an ambiguous coordinate-system error

   - Cause: the SpatialData object contains more than one valid table or coordinate system.
   - Fix: set ``table_key`` or ``coordinate_system`` explicitly.

3. No ROI identifiers matched

   - Cause: the CSV identifier type differs from the table instance key, or the same IDs occur in several regions.
   - Fix: confirm the exported identifier column and set ``roi_region`` for integrated data. Do not replace IDs with row numbers.

4. Polygon input is invalid

   - Cause: the ROI has fewer than three distinct vertices, self-intersects, or uses a different coordinate system.
   - Fix: export the polygon again and set the correct ``coordinate_system``.

5. The output Zarr is not substantially smaller

   - Cause: ``subset_mode=table`` deliberately retains complete spatial elements for downstream compatibility.
   - Fix: use ``subset_mode=spatial`` when synchronized Shapes/Points filtering is required, or ``split_by=image`` for a true rectangular crop.
